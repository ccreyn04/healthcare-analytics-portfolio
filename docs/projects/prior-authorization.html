Prior Authorization Access Dashboard

A patient-access and reimbursement case study tracking approvals, appeals, pending workload, case age, payer variation, and simulated savings protected.

Business question

How can a pharmacy access team prioritize authorization work to reduce delay, improve approval performance, and protect high-cost therapy access?

Project evidence

  • 700 synthetic authorization cases spanning five payers and eight drug classes.
  • Interactive filters for payer, drug class, outcome, and backlog age.
  • KPIs for approval share, active backlog, pending aging, decision time, and savings protected.
  • Searchable case evidence and PostgreSQL query pack.

Case study narrative

What the analysis demonstrates

Methodology

  1. Defined operational and financial KPIs before analysis.
  2. Validated required fields, status values, date ranges, and numeric columns.
  3. Segmented performance by the business dimensions most likely to guide action.
  4. Separated volume, rate, financial impact, and aging so priorities were not based on counts alone.
  5. Translated findings into a measurable operational recommendation.

Key findings

  • Approved cases represent 67.7% of all non-pending cases.
  • The active backlog contains 149 pending or appealed cases, including 41 pending cases over 10 days.
  • Total simulated savings protected is $2,363,098.
  • Payer approval share and case age vary enough to justify payer-specific documentation and escalation workflows.

Recommendations

  • Age active cases into 0–5, 6–10, and 11+ day workqueues with escalating ownership.
  • Create payer- and drug-class-specific documentation checklists for high-cost therapies.
  • Measure approval share, final appeal overturns, patient time-to-therapy, and abandoned cases separately in production.
  • Prioritize high-value cases using clinical urgency, case age, and potential financial impact—not value alone.

Limitations and next steps

  • The data is synthetic and does not include patient, provider, contract, staffing, or clinical-acuity details.
  • Estimated financial impact uses allowed or simulated savings amounts; it is not a guaranteed recovery value.
  • A production implementation should add data-quality checks, security controls, scheduled refreshes, ownership, targets, and validated business definitions.
  • The next build would connect the same logic to governed source systems and a production BI semantic model.
